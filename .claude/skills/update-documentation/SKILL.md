# Update Documentation

Sync project docs to the current state of the code. **Code is the source of truth** — when docs disagree with reality, rewrite the docs.

This skill is project-aware. It knows which docs exist, which sections drift fastest, and what the canonical sources are for each fact.

## Status Protocol

Emit a single status line before and after each phase:
- Format: `[Step N/7] <phase> — starting` / `[Step N/7] <phase> — done (<metric>)`
- Phases: 1=Parse Args & Guard, 2=Checkpoint, 3=Survey Code, 4=Audit & Rewrite, 5=Cross-check, 6=Report, 7=Cleanup
- Example: `[Step 4/7] Audit & Rewrite — done (12 files updated, 87 lines changed)`

---

## Safety Rules — READ FIRST

1. **Working tree must be clean before starting.** If `git status --porcelain` shows uncommitted changes, STOP and ask the user to commit or stash first. The checkpoint commit only works on a clean tree.
2. **Checkpoint before writing** — always create the snapshot commit first (per the user's version-control-safety memory). The user can revert the entire sync with `git reset --hard HEAD~1`.
3. **Memory files live outside the repo** at `~/.claude/projects/-Users-noyfisher-IOS-Projects-PT-Helper-Agent-v1/memory/`. Git checkpoint does NOT cover them — back them up separately to `/tmp/memory-backup-<timestamp>/` before rewriting.
4. **R1 applies — grep before rewriting any specific fact.** Never trust an old number, file count, or enum name from the doc itself. Always read the current source.
5. **Skip historical artifacts.** Do not touch point-in-time records: anything under `docs/archive/` or `scripts/archive/`, `virtual-users/results/**`, `CHANGELOG.md`, or anything under `vendor/`, `node_modules/`, `build/`, `DerivedData/`. Dated filenames (`*-YYYY-MM-DD.*`) are a reliable tell.
6. **Do not auto-commit the rewrites.** Leave them uncommitted so the user can review the diff before deciding to commit.
7. **Flag uncertain items rather than guessing.** If you can't verify a fact from code, leave the doc unchanged and report it in the "needs human input" section.

## Phase 3 — Survey the Codebase (Source of Truth)

## Phase 5 — Cross-check

Sequential sanity checks after all buckets have written:

1. **MEMORY.md ↔ memory files** — every `- [...](file.md)` link in MEMORY.md must resolve:
   ```bash
   cd ~/.claude/projects/-Users-noyfisher-IOS-Projects-PT-Helper-Agent-v1/memory && \
     grep -oE '\(([a-z_-]+\.md)\)' MEMORY.md | tr -d '()' | while read f; do
       [ -f "$f" ] || echo "ORPHAN LINK: $f"
     done
   ```

2. **CLAUDE.md cross-refs** — any path mentioned with backticks (e.g., `` `ios/PT-Helper/docs/manual-qa-checklist.md` ``) must exist:
   ```bash
   grep -oE '`[a-zA-Z0-9_/.-]+\.(md|swift|ts|json|py)`' /Users/noyfisher/IOS-Projects/PT-Helper-Agent-v1/CLAUDE.md | tr -d '`' | sort -u | while read p; do
     [ -f "/Users/noyfisher/IOS-Projects/PT-Helper-Agent-v1/$p" ] || echo "MISSING: $p"
   done
   ```

3. **Doc-internal links** — for each updated `docs/*.md`, verify any markdown link `[text](other.md)` resolves.

Collect all broken refs into a "needs human input" list for the final report. Do NOT auto-fix broken refs — the path is either wrong in the doc or the file was renamed; only the user can decide which.

## Phase 7 — Cleanup

1. **Do not run `git add`. Do not commit.** The user reviews `git diff` and decides.
2. Leave the working tree with uncommitted doc changes on top of the checkpoint commit.
3. If `$ARGUMENTS` was `dry-run`, the working tree should still be clean — verify with `git status --porcelain` and report any unexpected modifications.

---

## Dry-Run Mode

When `$ARGUMENTS == "dry-run"`:
- Skip Phase 2 (no checkpoint, no memory backup)
- Run Phase 3 surveys as normal
- In Phase 4, the agents must RETURN their planned changes but NOT write them. Adjust each agent prompt to say: "Return the planned changes as a structured JSON diff plan. Do not write any files."
- Skip Phase 5 (nothing to cross-check)
- Phase 6 report is the plan, not the result. Header should read "Documentation Sync — DRY RUN".

This lets the user preview the entire sync and approve before any writes happen.

---

## When NOT to use this skill

- For a single doc edit (just edit it directly).
- When code has just landed but isn't merged — wait for merge so the source of truth is stable.
- When the user is mid-feature and docs are intentionally ahead of code (e.g., writing a spec).
- For point-in-time artifacts like test reports or dated UX audits — those are records, not docs.
